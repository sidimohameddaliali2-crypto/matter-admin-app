# Matter application traceability

Implemented in Sidi's Delivery Admin source on 17 November 2026, from main commit `d4ad455`, rebased onto main `5ba9655`. Fixture checks below are distinct from the real deployment and authenticated browser verification required for activation.

The [route map](ROUTES.md) enumerates browser and API declarations with owning file/line references. The [JSON inventory](routes.json) also records response keys, inline status codes, referenced model/service calls, source digests, raw reporting dispatch evidence and Socket.IO event declarations. Regenerate it after changing a route or one of its owning files.

```sh
npm --prefix server run traceability:map
npm --prefix server run traceability:check
```

The normal server test suite checks that the generated map agrees with its source. The generator parses JavaScript and JSX without importing app entrypoints, connecting to databases, starting timers or contacting providers. Its input files are recorded by SHA-256 in `sourceDigests`. Static declarations include conditionally enabled routes. Registration order, nested routers and the Customer Service installer are preserved. Inline authorization predicates, indirect function calls, dynamic SDK behavior and imported report packages still require the linked source and runtime checks.

## Where to view it

In the app, open **Admin → Activity history** at `/traceability`. It opens on Issues, with one plain-language explanation per entry, a time and a Details control. All activity includes sentences such as “Osman added a driver” and “Osman assigned a delivery to Demo driver”. Search covers stored history and older results load by cursor. Details shows the person and available changes; account identifiers and additional recording information are further collapsed. History is private to exactly one release-configured existing account. Other accounts, including super-admins, cannot read history, the catalogue or diagnostics. Existing staff, partner and member authentication separately permits those accounts to report their own form activity without requiring history or Customer Service access.

Business activity is written to private, synced journal files and delivered idempotently to Mongo `activity_audit_events`. It survives an app restart and is shared through the database across app processes. The journal directory defaults to `server/.activity-journal`, is ignored by Git, and uses private directory/file permissions. Database outage leaves entries on disk for retry. No automatic expiry is applied to this history. A capture or storage failure is reported visibly. Technical HTTP/dependency diagnostics retain their separate 30-minute, 2,000-event process window and process log output. The local preview labels synthetic identity and records explicitly.

## What is captured

The server verifies the signed-in account name, ID and role. Browser actor claims are ignored. Identity is snapshotted after staff, Customer Service, partner or member authentication. Reporting sessions retain their original staff identity alongside report authority. Anonymous actions remain unidentified. System writes are labelled Automatic process. A name alone is insufficient to identify an account, so the underlying account ID is retained with each event.

Native input, textarea, select and contenteditable edits, submissions, native validation and scoped custom-form validation are recorded throughout authenticated app pages. Unsaved edits, submitted actions and confirmed database changes have separate stages. Login and public token-link pages do not collect unsaved input; their submitted server actions retain the authenticated or explicitly unidentified actor. The normal Add Driver entry point and assignment, reassignment and unassignment paths are exercised by isolated tests. Sensitive values are redacted before browser persistence and again at server ingestion. Form values are bounded excerpts, not full source-record copies.

Custom choices now report changes directly from their user handlers, including choices that never reach Save. These use the same private queue, server-verified identity and history as native fields. This includes maps and pins, selected delivery lists, stop ordering, calendars, quantities, chips, issue/action choices, dependent defaults, cleared values and discarded edits. The [custom-control coverage map](CONTROL_COVERAGE.md) records the mounted owning components and interpretation. Loading, polling and restoring an existing draft establish a baseline rather than inventing a new human edit.

Redacted browser events use an account-isolated IndexedDB queue, up to 5,000 entries without automatic expiry, with a 100-event send buffer and batches of at most 20 events/48 KB. Replay uses current authentication for the same account. Credentials and browser-provided actor claims are never persisted in that queue. Each value is capped at 300 characters and a submission summary includes up to 20 fields; individual native edit events are captured separately. A full queue or unavailable storage produces a visible gap warning. A browser crash before its asynchronous storage commit can still lose the latest input.

Mongoose save, query update/delete, insert and bulk-write paths are covered centrally. Confirmed document changes include available changed fields. Assignment changes resolve driver names while retaining reference IDs. Query-update previous values are observed before the write and can race with another edit; multi-record operations label sampled previous values and retain affected counts. Large/nested values are summarized and field excerpts are bounded. Transaction writes are confirmed only after commit; rollback entries remain unsaved. A partial batch failure must not be treated as proof that no records changed.

Raw tracker/GPS observations, capture batches and observation leases keep their existing owning evidence histories instead of being copied into staff activity. Successful automatic driver self-location pings without an explicit action reference are similarly excluded; errors and explicit staff location actions remain captured. This avoids duplicating continuous measurements and lease bookkeeping while preserving staff form and business changes. Location-only detection tolerates Mongoose's timestamp metadata, but never ignores additional business fields.

The canonical Customer Service cloud workflow adds its activity entry after the existing transaction commits. Its existing Supabase domain history remains authoritative and is preserved. Requests to provider systems, raw driver-report handlers and other native database paths retain response/attempt evidence; their internal persistence is confirmed by their owning history. This app cannot establish edits performed in another application's backend. New custom controls must report their accepted user changes through `recordActivityChange`; a DOM value set by JavaScript does not necessarily emit a native input event. Historical actions before feature activation are not reconstructed.

## How to follow a request

1. Reproduce the problem and read `X-Request-ID` on the response in browser Network tools. Staff, partner and member Axios clients also expose `response.requestId` or `error.requestId`. Rejected responses print that opaque reference and status in the browser console. Reloading creates new requests and references.
2. Search the API process's structured JSON output for that `request_id`. The `http.completed` record supplies the declared route template, method, elapsed time, status and outcome. URLs, query values, tokens and business payloads are excluded from this record.
3. Join `dependency.completed` records on `trace_id` or `request_id`. Nutrition and Truckoom outbound HTTP attempts are instrumented. `span_id` identifies an operation and `parent_span_id` joins it to the request or job that caused it. Cached responses can produce no outbound attempt. Provider transport completion can precede application validation of a provider's JSON result.
4. For scheduled work, search `job.started` and `job.completed` by `run_id`. Each execution has a fresh trace. Two runs with the same job name remain distinct. A started run without a completion can indicate process termination, unfinished work or missing logs. Check the process and scheduler before deciding which occurred.

This implementation restarts traces at the public HTTP boundary and does not trust caller-selected request IDs. It carries context within the Node process using AsyncLocalStorage. Trace headers are not sent to external providers. W3C propagation between approved first-party services and a collector/exporter are subsequent integration work.

## Interpreting diagnostic fields

| Field | Meaning and limits |
| --- | --- |
| `request_id` | Server-generated UUID for one HTTP attempt. A retry has a new request ID. This is a support reference and conveys no authorization. |
| `trace_id` | Random 32-character hex ID joining work within one execution. It conveys no business identity or proof of completion. |
| `span_id`, `parent_span_id` | Random 16-character operation IDs for parent-child relationships. |
| `run_id`, `job` | Random UUID per scheduled execution and a fixed job name. Run completion alone does not establish complete source coverage. |
| `route_id`, `route` | Source-derived method/path/file identifier and a static path template matched before dispatch. Conditional mounts or earlier handlers can change actual dispatch. Parameters stay placeholders. Raw delegated handlers use a declared boundary. |
| `status_code` | HTTP response or transport status. Zero represents a disconnect or transport failure without a received status. |
| `duration_ms` | Elapsed monotonic process time. Browser rendering, provider fix age and customer delivery time are separate clocks. |
| `completed` | The response finished or the wrapped operation returned. Inspect domain status, warnings, completeness and evidence separately. |
| `degraded` | The Truckoom vehicle route returned its existing fallback after the tracker dependency failed. Its HTTP response can remain 200. |
| `partial` | A job returned `complete: false` or a positive `failed` count. Other domain-specific partial outcomes still require service diagnostics. |
| `failed`, `server_error`, `timeout` | A wrapped operation failed, an HTTP response had a 5xx status, or a dependency reported a transport timeout. Raw error messages stay outside these new records. |
| `rejected` | An HTTP response had a 4xx status. This can represent denied access, invalid input, conflict, missing data or rate limits. |
| `disconnected` | The connection closed before response completion. The caller may retry after a write already committed. Check domain records and existing idempotency contracts. |
| `skipped` | Vehicle capture returned not-configured, already-running or already-claimed. A skipped run supplies no new capture. |
| `release` | Optional validated Git SHA from `MATTER_RELEASE_SHA`. Omitted when unset or invalid. |

HEAD can reuse a GET handler. Express may provide OPTIONS implicitly. Routes using `router.all` dispatch by method inside the handler. Statuses in the generated map come from inline `status`/`sendStatus` calls; default 200s, SDK responses, shared handlers and error middleware can supply additional statuses. Declared middleware is source evidence, not a permission audit. A GET can refresh caches or trigger background reads. Mutation routes can send notifications, upload evidence or write upstream even when no local database operation is visible inline.

## Data vocabulary and source ownership

Mongo models in `server/models` own Delivery Admin's operational records. The inventory's `referencedCalls` identifies direct imported model and service method calls inside inline handlers. Service calls can add database writes and provider work beyond those direct calls. Review the linked handler and service before using a route as a read-only probe.

`Delivery` links operational dispatch, proof and timing. `Customer` stores an operational customer identity and addresses. `User` supplies staff identity, driver profile and permissions. Bag and movement records track physical bag custody. Weekly menu, selection and order records represent dated food choices and partner/member orders. Vehicle capture and tracker event records represent observations with source provenance. Customer Service's canonical Supabase records represent conversations and workflow state. Reporting generations and evidence hashes bind a report to its inputs and policy. None of these identifiers should be copied into diagnostic metric labels.

Staff `protect` authenticates identity. `authorize`, role shortcuts and `checkPermission` constrain permitted actions. Partner and member middleware resolve their own scopes. `apiKeyAuth` authenticates the external read API. Customer Service and Driver Audit also perform their own session/readiness checks. OAuth consent and MCP scopes form another authority boundary. The map retains guard declarations without treating the presence of a function name as proof that all branches enforce it.

Schedules, enabled flags, leases, retry behavior and notification authority remain governed by the existing job code. Instrumentation runs around each execution. It does not create a scheduler, replay, new worker or capture feed. Jobs started in multiple processes still require their existing concurrency contracts.

Express requests, including early raw handlers, malformed JSON, denied auth and static files, receive a request reference and a completion record. Server errors, caller errors and disconnected responses are distinguished. The Stock/Driver/Partner/Member UI, offline replay and direct fetch callers all reach this HTTP boundary when online. The three shared Axios clients attach the response reference to their JavaScript result/error objects and associate recent write gestures with a browser action ID. Queued form events retain that ID. Existing operational offline queues, independent fetch calls and photo/status chains still have their own lifecycle and idempotency contracts; this gesture association is not proof that every related attempt belongs to one operation.

Socket.IO events are inventoried. Engine.IO bypasses Express request middleware, so the HTTP completion coverage does not include Socket.IO transport or individual event acknowledgement. Mongo/Redis/Postgres/Spaces calls, process resource metrics, browser rendering/errors, external worker internals and providers other than the instrumented Nutrition/Truckoom HTTP clients need further instrumentation. Existing business histories and reporting provenance continue to supply separate evidence.

## Privacy, operation and retention

Structured technical diagnostics use a fixed event/field allowlist and source-derived path templates. They exclude raw request/response bodies, URL queries, Authorization/Cookie headers, errors/stacks, customer/staff names, phone/email values, coordinates, files and provider secrets. Unknown routes are classified as a fixed unmatched/fallback template. The startup environment diagnostic records presence of a Mongo connection setting instead of printing its URI prefix. Request references are never authentication credentials. Private business history separately retains verified actor identity and bounded, redacted change excerpts for authorized history readers; those private records are not emitted to the diagnostic log sink.

Technical logging is enabled by default with process stdout as its sink and a 30-minute, 2,000-event in-memory diagnostic endpoint. `MATTER_TELEMETRY_ENABLED=0` disables structured diagnostics while request references and business capture remain available. Setting `MATTER_RELEASE_SHA` to a Git SHA adds release identity. Log-sink failures are contained. Business history adds the private journal and a collection in the app's existing Mongo database. No external collector, telemetry account or source-data export is added. Existing console statements elsewhere in the app have their own contents and require a separate review before forwarding entire process output.

The diagnostic memory window enforces its own 30-minute and 2,000-event bounds. Durable technical-log retention belongs to the selected process-log/collector infrastructure. Proposed starting limits are 14 days for diagnostic logs, 7 days for future sampled traces and 90 days for aggregate metrics, subject to an owner-approved storage/access policy. These periods are proposals and are not enforced by this patch. Business activity has no automatic expiry in this implementation. Journal and browser queue limits are explicit above; retained evidence and provider archives have independent policies.

Useful initial aggregates are request count, p95 duration, 4xx/5xx rate, degraded-200 count, dependency timeout/rejection rate, job last completion and start-without-completion counts. Group by fixed route, method, dependency, job and outcome. Keep request/trace/run IDs out of metric labels. Data freshness, queue age, processed/rejected totals, process health and source coverage need domain-specific measurements. Alert thresholds require a measured baseline.

## Private release setup

The existing production deployment passes the approved sign-in email through the private `MATTER_ACTIVITY_READER_EMAILS` environment secret. `node server/scripts/activityHistoryDeploy.js --apply` resolves exactly one active existing account and atomically saves its immutable account ID in owner-only `server/.private/activity-history/readers.json`, preserving a private previous-configuration receipt. It does not create users or change roles/page permissions. Missing, unsafe, inactive or multiple-reader configurations fail closed. Ordinary roles, editable permissions and client flags cannot grant history access.

Login/current-user responses derive `canViewActivityHistory` from this private ID. Navigation checks that flag before the super-admin shortcut, and the private route verifies the current session before mounting content. Account switches, cross-tab logout and profile-update responses cannot carry another session's history approval forward.

Before API restart, deployment checks database availability and private journal disk headroom. Afterwards `--verify` confirms exactly one active reader, denial for all other active accounts, unauthenticated API rejection and private journal readiness, emitting only safe counts/timestamps. The app then captures real activity with `preview: false`; examples are provided only by isolated development fixtures. Real authenticated form/action capture must be verified after deployment; deployment acceptance alone is not that evidence.
